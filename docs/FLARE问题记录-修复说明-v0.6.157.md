# v0.6.157 修复说明：重复调用误报与失败归因（问题记录 #25 / #26）

来源：`downloader-research/FLARE问题记录.md` 第 25、26 条（flare 优化 fluxdl 期间现场产生）。

## #25 「检测到重复调用工具「terminal」多次」——误报，且中止后上下文残缺

现场表现：模型在同一条回复里发出两个 `terminal` 调用（`ls` 一条、`python3 -c` 一条，
参数完全不同），flare 报「检测到重复调用工具「terminal」多次」并中断本轮。

三个独立缺陷叠在一起：

1. **签名只看工具名**。旧实现拿 `name` 做去重键，同批两个参数不同的 `terminal`
   天然撞键 —— 这等于禁止并行跑两条命令，而并行正是省时间的主要手段。
2. **判重逻辑用「窗口内合计次数」**。正常节奏「改一次代码、跑一次测试」也会把
   同一命令累计到 4 次而被误杀；只有「连续重复」才是卡死信号。
3. **中止时不补 tool 响应**。`break` 出去后，`assistant.tool_calls` 里那些没执行的
   调用没有对应的 `tool` 消息。协议要求每个 `tool_call_id` 都必须有响应，于是下一轮
   请求直接被上游判 400 invalid_request —— 而这段坏历史已经落库，`--continue`
   读回来还是坏的，会话彻底报废。

修法：

- `toolSignature()` 改为 `name + sha1(规范化后的完整参数 JSON)`（键排序、去空白），
  同批调用按签名去重；`countTrailingRepeats()` 只数**连续尾部**重复，中间夹了别的
  调用就不算卡死。
- 同批里参数完全相同的调用合并执行一次，其余调用返回「同批重复调用，已跳过（见前者结果）」
  的占位结果 —— 既省一次真实副作用，又保持上下文合法。
- 新增 `Agent.repairDanglingToolCalls()`：上送前扫描历史，缺哪条 `tool` 响应就补一条
  「未执行」占位；并在 `run()` 起始处先补再清理孤儿消息。旧做法是直接丢弃整对，
  等于把「模型上一步做过什么」从上下文里抹掉，续跑时它会重复劳动。
- 中止路径先补齐再抛错，保证落库的历史永远合法。

## #26 两个「假失败」

### 26-a 复合命令只报一个退出码

`a && b | c` 的退出码只反映最后执行的那一段 / 管道末端。模型看到 `退出码 1` 会去怀疑
被测命令，改本来正确的东西。现在失败信息里加段清单与定位方法：

```
命令执行失败（退出码 1）。复合命令共 2 段（1.python3 2.grep），
退出码只反映链上最后执行的那一段。定位失败段：把各段单独执行，或 `set -o pipefail` 后看 `${PIPESTATUS[@]}`
```

管道里用 `$?` 取退出码时额外提示改用 `${PIPESTATUS[0]}`。

### 26-b `curl … | python3 -m json.tool` 被当成「下载即执行」

`python3 -m json.tool` 只把 stdin 当 JSON 解析并美化，不 eval、不落盘执行，和 `| cat`
同级。旧规则只要「解释器 + 上游是下载器」就判 block，把最稳妥的查看方式拦下，逼模型
改用 `curl -o` + `python3 -c` 甚至 `sed` 拼字符串 —— 反而更危险。

现在只放行 `-m json.tool` 这一个纯格式化模块；`python3 -`、`python3 脚本`、`node -e`、
`bash` 等一律照旧拦截（有回归用例守着）。
